# 회고록 - 2026-08-07

## Keep (유지할 것)

- 에러 메시지 하나로 섣불리 결론 내지 않고, DB 스키마(`DESCRIBE`), 서버 로그, 실제 SQL을 직접 대조하며 원인을 끝까지 추적했다. `payments.license_tier_id`인 줄 알았던 500 에러가 사실은 이름만 같은 `subscriptions.license_tier_id`(레거시 컬럼) 때문이었다는 것도 이 과정에서 밝혀냈다.
- 프론트에서 못 고치는 문제(게이트웨이 라우팅, 인증 흐름)와 직접 고칠 수 있는 문제를 구분해서, 무리하게 프론트 쪽에서 우회하지 않고 원인을 정확히 짚어 담당자에게 넘겼다.
- 병합 과정에서 조용히 사라진 라이선스 등급 선택 UI를 사용자 리포트("구매 기능이 없어졌다")만 보고 코드에서 실제로 빠진 부분을 찾아 복원했다.
- 워터마크처럼 "미구현"이라고 문서에 적혀 있던 기능도 소스 코드를 직접 열어 재검증해서, 실제로는 구현돼 있다는 걸 바로잡았다.

## Problem (문제점)

- `ddl-auto: update`가 컬럼을 자동으로 지워주지 않아서, 예전 설계(디자이너별 구독가·구독 플랜 개념)의 흔적(`license_tier_id`, `plan_code`)이 DB에 그대로 남아있었다. 몇 주 전 폐기된 설계가 오늘 500 에러의 진짜 원인이 될 때까지 아무도 몰랐다.
- 공용 예외 핸들러(`GlobalExceptionHandler`)가 모든 예외를 "서버 오류가 발생했습니다"로 뭉개면서 로그에 스택 트레이스를 남기지 않아, 같은 500 에러의 원인을 찾는 데만 여러 라운드의 로그 확인이 필요했다.
- 프론트 두 팀 코드를 합치는 과정에서 라이선스 선택 UI가 통째로 빠지고, 구독 버튼 템플릿은 반대로 중복돼서 남는 등 병합 결과를 눈으로 검증하는 절차가 없었다.
- 구독 기능의 설계 전제가 세션 중간에 두 번 바뀌었다(디자이너별 가격 설정 → 실제로는 고정 정책). 실제 백엔드 계약을 먼저 확인하지 않고 프론트/기획을 먼저 짜면서 뒤늦게 뒤집는 일이 반복됐다.
- "기능을 통째로 뺄지 말지"를 두고 짧은 시간에 결정이 두 번 바뀌면서, 삭제 작업을 시작했다가 되돌리는 데 불필요한 왕복이 있었다.

## Try (다음에 시도할 것)

- 엔티티 필드를 지우거나 이름을 바꿀 때는 `ddl-auto`만 믿지 말고, 옛 컬럼을 정리하는 마이그레이션(ALTER/DROP)을 명시적으로 남긴다.
- 공용 예외 핸들러에는 최소한 `log.error(e)`를 항상 남긴다. 지금처럼 원인 불명 500이 반복될 때 로그만 보고도 바로 원인을 찾을 수 있어야 한다.
- 프론트 병합 후에는 로그인, 상세 페이지, 구매, 마이페이지처럼 핵심 플로우를 스모크 테스트 체크리스트로 한 번씩 직접 눌러본다.
- 새 기능(구독처럼 여러 서비스에 걸치는 기능)은 설계·프론트 작업을 시작하기 전에 실제 백엔드 컨트롤러/DTO를 먼저 확인하고 시작한다.
- 기능을 뺄지 고칠지 같은 방향 결정은 착수 전에 한 번 더 확인하고, 결정 즉시 바로 실행에 들어가지 않는다.
